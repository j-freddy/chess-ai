  sat inside the if value is None branch, so game-over values were backed up in
  White's perspective unconditionally. They were only correct when the leaf
  player happened to be White. Verified before the fix:

  WHITE mates -> leaf player is BLACK
    stored value for the MATING move = +1.00   -> mover sees this line as BAD
  BLACK mates -> leaf player is WHITE
    stored value for the MATING move = -1.00   -> mover sees this line as GOOD

  Concretely, with mate available at the root, the engine scored the mating move
  a1a8 at +1.00 for the side being mated and played g1h1 instead.
  _check_for_mate hid this at the root, but not deeper in the tree. Moved the
  flip out so it covers both branches. After: a1a8 scores -1.00, gets 77,375 of
  77,376 visits, and is played.

  2. Final move selected by UCB score (player.py/tree.py). choose_move returned
  root.select_child(), the same rule used to explore. UCB deliberately inflates
  rarely-visited children, which is the wrong bias when committing. It
  demonstrably picked a 3-visit child over a 4-visit one. Added
  Node.select_best_action() (most visits, value as tiebreak).

  3. Engine chatter on stdout (player.py). print(root) dumped ~30 lines of
  Node(...) and an ASCII board into the UCI channel, where a GUI parses it as
  protocol commands. Moved to stderr.

  4. go ignored all parameters (protocol.py). go movetime 100 thought for 5
  seconds. Now honours movetime, wtime/btime/winc/binc/movestogo, and infinite;
  depth/nodes/mate/searchmoves/ponder are still ignored but no longer break time
  control.

  5. go crashed on a finished game (protocol.py). Checkmate or stalemate raised
  ValueError: No legal moves, which killed the process. Now emits bestmove 0000.

  6. Deterministic playouts (player.py). playout took the argmax of the prior,
  so it was a pure function of the state — repeating it added zero information
  and num_playouts=4 cost 4x the time for an identical value. Now samples
  proportionally to the prior. Added an optional rng for reproducibility.

  7. Priors could be mispaired with moves (player.py). Root expansion zipped
  board.legal_moves against the model's probabilities while discarding the
  model's own move list. Correct only while a model enumerates moves in
  legal_moves order. Now uses the model's pairing, matching what the in-loop
  expansion already did.

  8. Minor: input() raising EOFError on pipe close produced a traceback; print
  calls now flush explicitly (previously they only flushed as a side effect of
  input()).

  Also fixed: throughput

  Profiling showed 7 simulations per second against 31 root moves — the search
  couldn't sample each move once, so the returned move was near-arbitrary. 94%
  of time was FEN parsing: statically_score_move rebuilt a chess.Board for every
  candidate move. Added score_move_on_board, keeping the tested
  statically_score_move(move, fen) signature. 7 → 38 simulations/sec.

  What I could not settle

  - Absolute strength is still weak. Even at 38 sims/sec the search barely
    covers 31 root moves. An 8-game match at 0.3s/move gave 4.5–3.5, which is
    noise. A 10-game match at 1.5s/move was still running when you called time.
  - The remaining bottleneck is a design issue, not a bug, so I left it. playout
    calls board.fen() and Model.predict re-parses it every ply, and the naive
    model does a push/is_checkmate/pop per legal move per ply. Fixing properly
    means letting Model.predict take a chess.Board instead of a FEN string — a
    change to the Model ABC I didn't want to make unasked.
  - ucb_score has no c_puct exploration constant. Not a bug, but it's the
    standard PUCT knob and is currently unavailable for tuning.
  - stop, ponderhit and info are still unimplemented. The engine is
    single-threaded, so it can't answer isready/stop mid-search. I capped go 
    infinite at 60s rather than hanging forever, but that's a workaround.
